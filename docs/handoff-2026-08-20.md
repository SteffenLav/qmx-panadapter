> ### The big one: a crash now survives the reboot (#117, was "Not started")
>
> A field crash used to leave **nothing** on the device — you would ask for a
> diagnostic download and get everything except the one thing needed. That is
> fixed and **verified end to end on hardware**, not by reading the code:
>
> * The panic handler stashes a record in RTC no-init RAM; the next boot logs it
>   into the ring, `/api/log` **and** `/api/log/saved`.
> * It carries the reason, the assert text, **which task died**, how far into the
>   run, the registers, and a ready-made `addr2line` line.
> * I crashed the device deliberately and the next boot reported
>   `task httpd, core 0, after 18.334 s, abort() was called at PC 0x4806acfd` —
>   and that PC decodes to **webserver.c:848**, the exact `abort()` line.
> * A valid record is also **positive proof** the reset was a real crash, which
>   `reset_reason` never could be here.
>
> I deliberately did **not** use the design the TODO proposed (flush to flash
> from the handler): a panic handler runs with interrupts off and the cache
> possibly disabled, so a SPIFFS write there can hang instead of rebooting —
> turning a diagnosable crash into a dead device.
>
> New dev action `{"action":"panic_test"}` crashes on demand so the mechanism
> stays falsifiable. ⚠ **Radio-off only** — a panic reboot is a warm reset, the
> #74 trigger.

> ### #199 root-caused, and it was one bug in two places
>
> The `tlsf_free` double-free reboot **open and unreproduced since v1.3.0** now
> has a cause: `s_ft8_task_alive` was set as `ft8_task`'s first statement, so it

### 201 + 202 — one fault, FIXED (`aa5b6e3`)

`ft8_robot_occupancy_ready()` requires having **received** in both time windows
within four slot periods. But you cannot receive in a window you are
**transmitting** in — so our own TX made that parity look unheard and the gate
concluded the band was unmapped. Every `auto-answer holding: both transmit
windows not mapped yet` in his log follows our own transmission, two of them
30 s apart right after a completed QSO. That is his "waits 30 seconds, by then
the POTA CQ station has likely moved on", and it is why it was intermittent:
it only happens *after* a QSO, never from a cold start.

His strips were correct all along — they are built from accumulated data and
quite properly still showed green.

The state was never recorded anywhere. `s_last_rx_utc_even/odd` carries a comment
naming exactly this case (*"we were transmitting into this window and have no
idea"*) and nothing tracked it. Added `s_last_tx_utc_*`, set at both TX sites.

**Also fixed: `⚠ FREQ BUSY` was a SCREEN-ONLY state.** He photographed it and sent
29 minutes of log in which the string never appears — the report could not be
investigated at all. It now logs on change, with the occupancy picture alongside,
because the question is always "busy according to what?"

### 203 — a SEPARATE and more serious fault, ROOT-CAUSED, **NOT FIXED**

**The grey strips were honest: there was no data.**

```
decodes/min:  min 26 = 111,  min 27 = (none),  min 28 = (none),  min 29 = 39
```

A **~2-minute total decode blackout**. The decode list ages at 60 s, so the
occupancy map emptied and both strips went grey — matching his "after 2 more
all-grey cycles the mapping resumed" exactly.

Cause: **the audio ring overflowed.**

```
W audio: RX 49081 pairs/s ... DROPPED=49936 (ring full)
I dsp: FT8 cap: ... active=0
```

The QMX kept delivering ~49k pairs/s the whole time while essentially every
sample was thrown away, because nothing was draining the ring. Slot completions
pin it: slot 102 → 103 took 24 s (already stretched from ~15), then **slot 103 →
104 took 117 SECONDS**. `fft_task`, the ring's sole consumer, stopped for two
minutes.

Bounded rather than chronic: all 125 `DROPPED` lines in the session fall in
minutes 26–28, plus one benign line at startup.

⚠ **WHY it stalled is NOT established.** Correlates in that window, none proven
causal: internal heap sliding 33 → 27 → **22 KB with `lblk=12KB LOW!`**; dense
HTTPS feed activity (several TLS handshakes, a 33 KB POTA fetch, a PSK Reporter
send, update_check); a WS client connected; two SDIO oversize recoveries.

⭐ **Test this candidate first:** device TLS runs on **software crypto** because
hardware AES cannot get DMA descriptors (see the TLS/DMA note in CLAUDE.md), so
concurrent HTTPS handshakes are unusually expensive — on a board where `fft_task`
is priority 4 on core 1. A task at priority 6 caused exactly this class of
starvation before (the CW-audio task, #51 era).

**This is the #51 signature — audio lost, decodes collapse — arriving through ring
overflow rather than the USB wire, on a released build with a user watching.**
Reproduce by driving the feeds hard during FT8 and watching for `DROPPED=`.

## 3. Mark G4MEM — Cloudlog was broken for everyone, FIXED (`1485904`)

He hit "is not on this network" within hours of v1.8.7 and **correctly identified
the cause himself.** Confirmed from the IDF headers rather than taken on trust:
`esp_ip4_addr1()` is `byte[0]`, so esp_netif stores **network** byte order. On
this little-endian CPU his server read as `0x0801A8C0` against a parsed
`0xC0A80108`, and a 255.255.255.0 netmask arrived as `0x00FFFFFF` — so the masked
equality compared the **wrong end** of the address. No LAN server could ever have
matched.

⚠ **Why the tests passed, and this is the lesson worth keeping.** Every case in
the harness built BOTH sides with its own host-order helper, so the suite compared
a convention against itself. The mutation run could not find it either:
`net_guard.c` was internally correct and the defect was in the **caller's**
conversion, outside the unit under test. *A harness that supplies its own inputs
can only test the half of the interface it owns.*

New cases start from the raw bytes esp_netif produces, include his exact setup,
and assert that raw network-order values must **not** appear to work.
Re-mutation-tested.

His other suspicion is fine: a URL with a path suffix (`192.168.1.8/cloudlog`)
parses correctly.
