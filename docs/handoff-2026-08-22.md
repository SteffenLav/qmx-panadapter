## 2. NOT YET RELEASED: the OTA-failed-pulse feature (2 commits on `main`)

Randy N4OPI reported the accept-gesture felt "flimsy" during the v1.9.2 OTA
test. Root-caused via the 2nd Tab5's own diag log (see below) — **the gesture
itself was never the problem**; it fired correctly on every single attempt,
including two genuinely FAILED downloads back on v1.9.0/v1.9.1. What failed
was the download, and a correctly-registered press followed by an
instantly-failed download looked identical to the press not registering.

Fix (`ab0a7ab`): `"Server busy - tap retries"` now **pulses** (fast opacity
breathe, 350ms each way, ~4 cycles over 3s — NOT a 1Hz colour swap, which was
tried first and was too subtle to read as blinking), then quietly reverts to
the plain version line after `OTA_FAILED_SHOW_S` (3s, tuned down from an
initial 20s per the operator). Tap-and-hold still retries the whole time.

Two real bugs found and fixed live on hardware while testing this
(`614a07d`), both worth remembering as a class:

- **Cross-thread LVGL corruption with no crash at all.** The pulse's
  `lv_anim_start()`/`lv_anim_del()` were called from `status_task` without
  `display_lock()` — the one discipline every other touch to this label
  already follows. Result: the device stayed completely healthy (FT8/CAT/
  WiFi all fine, no assert anywhere in the log) but the bottom-bar label got
  permanently stuck after the first pulse — every later write to it, from
  any source, silently stopped taking effect. Best explanation: LVGL's own
  redraw loop hung traversing a corrupted anim list, so `display_lock()`
  timed out forever after, and every caller here already treats a failed
  lock as "do nothing". **Lesson: `lv_anim_*` calls need `display_lock()`
  exactly like any other LVGL touch — it is not a special/thread-safe API.**
- **State-based "is this new" detection breaks when the state is instant.**
  `ota_failed_ticks` only reset to 0 when `OTA_RUNNING`/`OTA_DONE` were
  *observed* at 1 Hz — but a bad-hostname failure completes in **under
  100ms** (measured), so the 1 Hz poll can go straight from one FAILED tick
  to the next FAILED tick of a brand new attempt with no observable state
  change between them. Fixed with a monotonic `ota_update_get_fail_seq()`
  (bumped in `set_failed()`), compared against a remembered value — the
  general pattern: **when you need to detect "a new X happened" and X can be
  faster than your poll rate, don't infer it from state transitions; use an
  explicit counter.**

**Verified on the dev Tab5** by repeatedly firing a real (harmless) failure
via `{"action":"ota_install","url":"https://example.invalid/nope.bin"}` and
watching the serial log live to call the exact moment. Confirmed: pulses
correctly, reverts correctly, no stuck state, works on repeated back-to-back
failures.

tag + build + flash — same process as every other release. Both dev and the
2nd Tab5 will need reflashing (2nd only if you say so, per the standing

## 4. FT8 QSO fix #234 — shipped, but NOT reproduced against the exact scenario

Root-caused entirely from Roy's diagnostic log + code reading (no live
repro): `ft8_qso_start()`'s only "skip past TX1" special-case checked
`kind == FT8_TX_KIND_REPLY`, missing `FT8_TX_KIND_ROGER_RPT` (built when the
partner's own first message was already a report), so it defaulted to
`WAIT_RPT` instead of `WAIT_RR73` and never recognised a bare `RRR`.
Regression-tested in FT8 simulation mode (a full QSO through the exact
`WAIT_RPT`/`WAIT_RR73` transition completed and logged normally), but **sim's
phantoms don't organically produce Roy's exact 3-message sequence** (a
partner whose first message to us is already a report, reached via the
auto-pileup drain). If he reports it again after v1.9.2, that's real signal
the fix is incomplete, not just "needs more testing".
